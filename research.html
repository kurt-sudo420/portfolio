Current experiment

Won't, or can't?

When a model refuses a harmful request, is the refusal doing the work, or is the model simply unable to do the task? The study removes the refusal direction with weight editing and re-scans under identical conditions.

Hypothesis

Refusal-mediated resistance

Attacks the model resists because it chooses to refuse. If refusal is doing the work, resistance should collapse once the refusal direction is removed.

resistanceexpected to collapse

Capability-mediated resistance

Attacks the model resists because it can't carry them out, like decoding encoded payloads. This is the control: it should stay roughly where it was.

resistanceexpected to hold

Bars sketch the hypothesis; they are not measured results.

Method

Reproducible by design

Most of reproducibility is logistics. These are the rules every run follows. See the HYDRA case study

Pinned stack

vLLM 0.6.3, torch 2.4.0, and transformers 4.46.3, matched to the node's CUDA 12.2 driver.

Identical parameters

Same probes, generation settings, and seeds for every before-and-after pair.

Same-day baselines

The baseline is re-run on the same day as the comparison to rule out configuration drift.

Read the hit logs

Pass rates are checked against what the model actually said, then placed against a calibration baseline.

Threat model

The attack surface

Red-team output is only as useful as the taxonomy you read it with. These are the attack classes my scans are designed to surface, and the defenses that correspond to each.

Jailbreaks

Persuading a model to set aside its own guidelines. Single-turn variants convince it to caveat rather than refuse; multi-turn variants escalate gradually until it has drifted past a boundary it would have enforced if asked directly.

Corresponding defenses

Input / output filtersSystem prompt hardeningSafety fine-tuningSecond-model verification

Prompt injection

Instructions smuggled into content a model ingests rather than typed by its operator. Highly relevant to SOC work, because the tooling analysts rely on can itself be a target.

Corresponding defenses

Input / output sanitizationSensitive data labelingAgent identity and access controlInformation flow control

Hallucination

A failure mode rather than an attack: the model asserts something false and, asked to verify, confirms it. The adversarial angle is inducing or exploiting it.

Corresponding defenses

Retrieval groundingGroundedness detectorsOutput validation

Reasoning-chain attacks

Hidden triggers that hijack the step-by-step process a model uses to decompose a problem, steering it toward a malicious result even when the request looks benign.

Corresponding defenses

Reasoning-based safety trainingModel evaluationChain inspection

Cross-modal injection

Instructions carried in an image or audio channel that a multimodal model ingests, routing straight past defenses that only inspect the text prompt.

Corresponding defenses

Multimodal input inspectionCross-channel sanitizationProvenance tracking

A distinction worth keeping straight. PyRIT and garak are offensive instrumentation, not controls. They tell you whether a weakness exists; they don't prevent it. Treating a scanner as a safeguard is how a team ends up with a clean report and an unguarded model.

Defense in depth

Where guardrails live

A model can be well aligned and still be deployed into a system with no controls around it. Conflating the two layers is a common mistake.

Model-level

Built into the model
  • Training data quality
  • Safety alignment and refusal training
  • Reasoning-based safety training

System-level

Wrapped around the deployed model
  • Runtime guardrail tooling
  • Content moderation and adversarial robustness
  • Factuality verifiers such as MiniCheck
  • Copyright and privacy leakage detection

Responsible research

How the work is bounded

Offensive testing is only legitimate inside a protocol. These boundaries are a condition of approval for the group's work, and I'd expect to work to the same standard anywhere else.

Authorized targets only

Models the group hosts locally, and devices owned by or provided for the group. Nothing third-party, production, or non-consenting.

Isolation

Model servers sit behind authenticated SSH tunnels; hardware testing happens on an air-gapped bench.

Oversight and disclosure

My mentor reviews scope before each new exploit class. Real-world findings go through coordinated disclosure.

Data handling

No private, regulated, or personally identifying data. Datasets are synthetic or public.

The objective is characterization, not distribution. The point is to describe vulnerabilities well enough to defend against them, producing a paper and a findings report rather than shipping working attacks.
