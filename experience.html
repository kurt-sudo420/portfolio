Domain knowledge

The LLM threat model I work against

Red-team output is only as useful as the taxonomy you read it with. These are the attack classes my scans are designed to surface, and the defenses that actually correspond to each one.

Jailbreaks

Persuading a model to set aside its own guidelines. Single-turn variants convince the model to amend its rules so it caveats rather than refuses; multi-turn variants escalate gradually across a conversation until the model has drifted past the boundary it would have enforced if asked directly.

Corresponding defenses

Input / Output Filters System Prompt Hardening Safety Fine-Tuning Second-Model Verification

Prompt injection

Instructions smuggled into content a model ingests rather than typed by its operator. It's the class I find most relevant to SOC work, because the same tooling analysts rely on can itself be a target — a publicly reported case involved a file submitted to a malware-analysis service carrying instructions the analyzing agent then followed.

Corresponding defenses

Input / Output Sanitization Sensitive Data Labeling Agent Identity & Access Control Information Flow Control

Hallucination

A failure mode rather than an attack in its own right — the model asserts something false and, asked to verify, confirms it. The adversarial angle is inducing or exploiting it, which makes it a security concern and not just a quality one.

Corresponding defenses

Retrieval Grounding (RAG) Groundedness Detectors Output Validation

Reasoning-chain attacks

Hidden triggers that hijack the step-by-step process a model uses to decompose a complex problem, steering the chain toward a malicious result even where the surface request looks benign.

Corresponding defenses

Reasoning-Based Safety Training Model Evaluation Chain Inspection

Cross-modal indirect injection

The class I'm building toward now. Injection doesn't have to arrive as text — instructions can be carried in an image or an audio channel that a multimodal model ingests, which routes straight past defenses that only inspect the text prompt. Reproducing the Nassi et al. work from Black Hat Europe 2023 and extending the BadToken scanner with an image-based exploit module is the next thing I'm building.

Corresponding defenses

Multimodal Input Inspection Cross-Channel Sanitization Information Flow Control Provenance Tracking

A distinction worth keeping straight. PyRIT and garak are offensive instrumentation, not controls. They orchestrate attack prompts, score the responses, and iterate — they tell you whether a weakness exists, they don't prevent it. Treating a scanner as a safeguard is how a team ends up with a clean report and an unguarded model.

Defense in depth

Where guardrails actually live

Defenses sit at two layers, and conflating them is a common mistake — a model can be well aligned and still be deployed into a system with no controls around it.

Model-level

Baked into the model itself

  • Training data quality — what the model learned from in the first place
  • Safety alignment — refusal training on harmful requests
  • Reasoning-based safety training — hardening the chain, not just the output

System-level

Wrapped around the deployed model

  • Guardrail tooling — runtime safety controls at the boundary
  • Content moderation & adversarial robustness
  • Factuality verifiers — groundedness checking such as MiniCheck
  • Copyright infringement detection
  • Privacy leakage detection

Scope & responsible use

How this work is bounded

Offensive testing is only legitimate inside a protocol. These boundaries govern all of the group's testing and are a condition of approval for the work, not preferences I set for myself — and I'd expect to work to the same standard anywhere else.

Authorized targets only

Model testing is limited to instances the research group hosts locally. Hardware testing is limited to devices, tags, and credentials owned by or explicitly provided for the group. Nothing is tested against third-party, production, or non-consenting systems.

Isolation

Model servers are reachable only through authenticated SSH tunnels; hardware testing happens on an air-gapped bench. No exploit is ever exercised against live campus infrastructure.

Faculty oversight & disclosure

My mentor reviews scope before each new exploit class is introduced. Any finding with real-world disclosure implications goes through coordinated, responsible disclosure rather than publication.

Data handling

No private, regulated, or personally identifying data is used in testing. Datasets are synthetic or public, and results stay inside the group and its disclosure process.

The objective is characterization, not distribution. The point of the work is to discover and describe vulnerabilities well enough to defend against them — producing a research paper and a findings report, not shipping working attacks.
