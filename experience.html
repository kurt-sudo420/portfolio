Case walkthroughs

How I work an alert

Three kinds of case from the queue, replayed one stage at a time. Every value is invented: the domains, addresses, hostnames, and counts don't exist anywhere.

Illustrative walkthrough

Synthetic data

  1. Signal

    A user reports a suspicious message

    A staff member uses the report button on an email asking them to review a shared document. Reports like this are the cheapest detection there is, so each one gets a real look.

    source
    user report
    subject
    Shared file: Q3 budget review
    sender
    accounts@billing-notice.example
    queue
    email security

  2. Triage

    Read the headers before the body

    The display name imitates an internal department, but the sending domain doesn't belong to the university and the Reply-To points somewhere else again. Authentication results settle it.

    Decision Not a false report. Treat as phishing and keep going.

    spf
    fail
    dkim
    none
    dmarc
    fail
    reply-to
    mismatch with sender

  3. Enrich

    Find out what the link does

    The URL is checked against threat intelligence, then opened in a sandbox rather than on a workstation. A recently registered domain serving a copy of a sign-in page is credential phishing, not spam.

    Decision Credential harvesting confirmed. Scope it.

    url
    hxxps://docs-share[.]example/view
    domain age
    4 days
    reputation
    flagged
    sandbox
    fake sign-in page

  4. Scope

    Find everyone else who got it

    One report rarely means one recipient. A message trace shows who else received it and who clicked, and sign-in activity for those accounts gets reviewed next.

    Decision Two accounts need follow-up. The rest need the message removed.

    recipients
    14
    clicked
    2
    credentials entered
    1 suspected
    related cases
    unusual sign-in

  5. Respond

    Contain it, inside the runbook

    The message is removed from mailboxes, the sender and URL are blocked, and affected accounts get a password reset with sessions revoked. Anything outside my permissions goes to a senior analyst with the evidence attached.

    message
    removed
    sender and url
    blocked
    accounts
    reset, sessions revoked
    escalation
    senior analyst

  6. Record

    Write it up so the next analyst can use it

    Findings go into the ticket mapped to MITRE ATT&CK, with indicators listed so they can be searched later. If the same lure shows up again, the second case starts from this one.

    technique
    T1566.002 Spearphishing Link
    indicators
    1 domain, 1 url, 1 sender
    ticket
    closed with findings

  1. Signal

    Two sign-ins that can't both be the same person

    The SIEM raises an alert: one account signs in from Boston, then from another continent forty minutes later.

    account
    jdoe (synthetic)
    sign-in 1
    198.51.100.24, Boston
    sign-in 2
    203.0.113.77, overseas
    gap
    40 minutes

  2. Triage

    Rule out the boring explanations first

    Most of these are a VPN, a phone on a carrier network, or real travel. Device, client, and MFA details usually say which. Here the second sign-in is an unregistered device, and the MFA prompt was approved anyway.

    Decision No benign explanation fits. Investigate as a compromised account.

    device
    unregistered
    client
    new browser profile
    mfa
    push approved
    vpn match
    no

  3. Enrich

    Look at where it came from

    The second address belongs to a hosting provider the account has never used. Recent history adds context: the same user reported a phishing email two days earlier.

    Decision Likely credential theft from the phishing case. Link the two.

    ip owner
    hosting provider
    reputation
    flagged
    prior use
    none
    linked case
    reported phishing email

  4. Scope

    Find out what the session did

    What matters is what happened after sign-in: new inbox rules, forwarding, changes to MFA methods, files opened. A rule that quietly moves replies out of the inbox is a common way to hide.

    Decision Mailbox tampering found. Contain now.

    inbox rule
    created, hides replies
    forwarding
    none
    mfa methods
    unchanged
    mail sent
    0

  5. Respond

    Cut off access and undo the changes

    Sessions are revoked, credentials reset, the rule removed, and MFA re-registered with the user. Account actions I can't take myself are escalated with the timeline attached.

    sessions
    revoked
    password
    reset
    inbox rule
    removed
    mfa
    re-registered

  6. Record

    Close the loop with the phishing case

    The write-up records both techniques and ties this case to the email that started it, so the full chain is in one place.

    technique
    T1078 Valid Accounts
    technique
    T1564.008 Email Hiding Rules
    ticket
    closed, linked

  1. Signal

    A scan flags a critical finding

    The scanning agent on a workstation reports an outdated browser runtime with a critical vulnerability.

    asset
    WS-LAB-0142 (synthetic)
    finding
    outdated browser runtime
    severity
    critical, CVSS 9.8
    id
    CVE-0000-00000 (placeholder)

  2. Triage

    Confirm it's real

    Scanners report stale data and duplicates. Installed version against fixed version, the agent's last check-in, and whether the asset still exists all get checked before anyone is asked to patch.

    Decision True positive on a live machine.

    installed
    older than fixed version
    last check-in
    today
    duplicate asset
    no

  3. Enrich

    Decide how much it matters

    Severity alone isn't priority. The NVD entry gives the attack vector, and a listing in a known-exploited catalog means attackers are already using it. What the machine can reach matters too.

    Decision Exploited in the wild and network-reachable. Move it up the queue.

    vector
    network, no privileges
    known exploited
    yes
    exposure
    user workstation

  4. Scope

    Find every machine with the same problem

    Asset tags by hostname and address range turn one finding into a list: every endpoint running the same software version.

    affected endpoints
    23
    tag groups
    2
    already patched
    5

  5. Respond

    Propose a fix someone can act on

    The remediation proposal orders the work by exploitability and exposure, names the owning team, and sets a date. It goes to them as a ticket rather than a spreadsheet.

    order
    exposed machines first
    owner
    desktop support
    ticket
    opened

  6. Record

    Rescan, then close

    A finding is closed when a fresh scan says so, not when a patch is reported as installed. Before-and-after results go in the ticket.

    rescan
    clean
    evidence
    before and after attached
    ticket
    closed

This shows method, not history. It isn't a record of any real incident, and it leaves out how the university's environment is configured.
